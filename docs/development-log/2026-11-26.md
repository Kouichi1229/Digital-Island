## 二、環境感知與資料驗證

### 2.1 Raw Tile Observation

建立 `EnvironmentPerception.ts`，讓 Phaser 依 Lumi 當前座標取得指定半徑內的 Tile observations。每筆資料目前包含：

- 圖層名稱與 Tile index
- Tile 中心座標
- Lumi 到 Tile 中心的距離
- Phaser runtime 的碰撞狀態（`isCollidable`）

環境快照會隨 Lumi 移動更新。Environment Recorder 以至少 1 秒的間隔記錄環境資料。

### 2.2 感知測試

- 已完成靜止與移動狀態的環境感知測試。
- 移動時，感知中心與 nearby tiles 會隨 Lumi 位置改變。
- 感知半徑維持 96 px。
- 對 8,056 筆 runtime tile observations 進行地圖格位與 GID cross-reference，結果全部吻合；目前資料欄位名稱仍為 `tileIndex`，後續 schema 設計需明確區分 GID 與 tileset local ID。

### 2.3 Tile Collision 事件紀錄

- 在 Phaser 中啟用 Lumi 的 tile collision event，並將碰撞事件寫入 Environment Recorder。
- 碰撞紀錄包含時間、Lumi 座標、目標圖層、Tile index/GID 與目標座標。
- 同一個 Tile 在單次遊戲中只記錄首次碰撞，避免重複事件。
- Phase 2 測試資料包含 117 snapshots、71 collisions；71 筆碰撞均有完整欄位，且都能對應到曾出現在 nearbyTiles 的可碰撞 Tile。
- 目前已驗證碰撞事件能觸發並保存；測試資料尚不足以單獨證明所有情況下角色都確實受到物理阻擋，這部分仍需更直接的位移與速度證據。

### 2.4 Tile 語意與空間群組分析

完成 tileset metadata、GID 使用情況與空間相鄰群組的盤點。重要結論：

- `blocked` 是 tileset metadata；`isCollidable` 是 Phaser runtime 狀態，兩者不能混為同一概念。
- Tile 相鄰或 GID 不同，不能直接推定為同一個環境物件。
- Tile 數量不能直接當成物件數量。
- 部分使用中的 GID 尚未出現在 runtime observations，語意仍待確認。
- Ocean 的 GID 141、部分地面與懸崖 Tile 的用途仍有未知項目，不應自行補上未經驗證的語意。

### 2.5 已確立的環境感知架構方向

環境資料規劃分為四個概念層：

1. **Raw Tile Observation**：保留遊戲實際觀察到的 Tile 資料。
2. **Spatial Candidate Group**：依空間鄰接規則形成候選群組，必須標示為候選，不代表已確認物件。
3. **Confirmed Environment Object**：只有具備足夠證據時才可確認為環境物件；候選群組不得自動升級。
4. **Environment Region**：獨立描述區域，不與物件群組混為一談。

採用靜態地圖預處理候選群組、執行時依 Lumi 的實際感知範圍查詢附近資料的方向。AI 輸入以即時感知為主，靜態地圖資訊為輔，不傳送整張地圖的全部候選群組。

## 三、Vision Perception 設計

已確認第一階段視野設計：

- 以 Lumi 面向方向為中心，採前方 180° 視野（左右各 90°）。
- 暫定視野距離 96 px，以 Lumi 到目標 Tile 中心的距離計算。
- 先處理方向與距離，第一階段不處理視線遮蔽。
- 後方半圓不納入視野。
- 第二階段再加入 Line of Sight / Occlusion。

第二階段遮蔽設計方向：

- Nature、Rocks、Cliff_Details 等遮擋 Tile 參與視線遮蔽。
- 以 Lumi 到目標 Tile 中心的射線判斷；中間若經過遮擋 Tile，目標不可見，遮擋物本身仍可見。
- 不可直接將 `blocked` 或 `isCollidable` 當成已驗證的視線遮蔽屬性。
- 未定義或未知的遮蔽屬性，設計上傾向保守處理；實作前仍須確認 Phaser runtime 能否正確讀取 TSX metadata，並以測試驗證。

以上為設計決策，尚不代表 Vision Perception 與遮蔽功能已完成實作。

## 四、Lumi AI Backend

### 4.1 Backend API 與前後端通訊

Backend 使用 Express + TypeScript，已建立以下 API：

- `GET /api/health`：Backend 健康檢查。
- `GET /api/lumi/state`：取得 Lumi Controller 狀態。
- `POST /api/lumi/decide`：提交觀察資料並取得行動決策。
- `POST /api/lumi/complete`：回報行動完成，並驗證 actionId。
- `POST /api/lumi/recover`：手動要求 Controller 從 error 狀態恢復。

Vite proxy 已設定將前端 `/api` 請求轉送至 Backend。已透過 curl 驗證 Express、Vite proxy 與前後端 HTTP 通訊。

### 4.2 Lumi Persona 與 Memory

新增 Lumi Persona 與 Memory 基礎模組。

Persona 定義 Lumi 是剛開始獨立生活的年輕數碼獸：具備基本認知與常識，但尚不熟悉島嶼的具體地形與資源分布。Lumi 可以自由決定生活方式，不需要完成觀察者指定的任務。

Memory 模組目前提供觀察、經驗、想法與生活筆記等記憶資料結構及記錄函式。記憶容量管理、輸入驗證與完整生命週期仍待後續設計。

### 4.3 行動決策與 Controller

- 行動類型：`move_up`、`move_down`、`move_left`、`move_right`、`stop`。
- 每次行動由 Lumi 自行選擇方向或停止，以及持續時間。
- Backend 產生唯一 `actionId`；完成回報必須帶回相同 ID。
- Controller 拒絕過期、重複或不匹配的 actionId，避免舊完成事件改變目前行動狀態。
- Controller 狀態包含 `idle`、`deciding`、`acting`、`error`。

### 4.4 Gemini Provider 與 503 重試

因本機 Ollama 在目前硬體環境下造成明顯資源負擔，已將 Gemini 設為預設決策 Provider，Ollama 保留為可選 Provider。API Key 僅存放於 Backend 的 `.env`，並確認沒有加入 Git 暫存或提交。

Gemini 呼叫目前對 HTTP 503 採三次嘗試，重試等待時間為 2 秒、4 秒。測試已確認連續 503 時會依序重試並讓 Controller 進入 error；曾成功取得過一次合法 JSON 行動決策，但 Gemini 後續仍出現 high demand 503，因此服務可用性尚不穩定。

模型 metadata 查詢成功不等於實際生成推論一定可用，仍須以真實決策請求驗證。

## 五、Lumi 自主行動時間調整

為降低模型決策呼叫頻率，已將每次行動時間由原先 1–10 秒調整為：

- 最短 180 秒（3 分鐘）
- 最長 300 秒（5 分鐘）
- 移動與 `stop` 均適用
- 時間由 Lumi 自行決定，單位為現實世界秒數
- 行動結束後重新取得環境觀察，再向 Gemini 請求下一次決策

已同步調整 AI prompt、Gemini response schema、Action Parser 與 Phaser action validator。Parser 邊界測試結果：

Backend TypeScript 檢查與 Frontend production build 均已成功。Vite 仍有既有 bundle chunk 大於 500 KB 的警告，未影響本次 build 成功。

## 六、Gemini 故障後自動恢復：已確認方向，尚未實作

今日確認 Gemini 持續回傳 503、Controller 進入 error 時，Lumi 應保持安全靜止。Backend 應定期檢查 Gemini 是否恢復；確認服務可用後，恢復 Controller 並取得新的環境觀察，再要求 Lumi 做出全新決策，不需要觀察者人工介入。

明確限制：

- 不自動切換至 Ollama。
- 不自行編造或沿用舊行動。
- Gemini 尚未恢復時，Lumi 保持靜止。
- 恢復後必須重新觀察並產生新決策。

目前 Backend 只有手動 recovery API，Frontend 在決策失敗後也會停止自主循環；自動輪詢、恢復後重新啟動決策循環、輪詢間隔、退避策略及併發保護仍待設計與實作。現有 `checkGeminiReady()` 使用模型 metadata 查詢，不能單獨證明生成推論已恢復。
